## はじめに

仕様書を作ってAIに実装してもらうと、テストは全部通っているのに、よく見ると本来の意図とは少し違う実装になっていた、ということがあると思います。AIがテストに合わせて答え合わせのように作ってしまうと、そのずれに気づかないまま開発が進んでしまいます。

AIのコードレビューについて海外の記事を調べていたところ、これに関係する「Isolated Specification Tests」という考え方を見つけました。2026年7月にcodecentricのMarcel Miklさんが書いた記事で紹介されていたものです。

https://www.codecentric.de/en/knowledge-hub/blog/ai-code-review-loop-verification

Zennではまだ紹介している記事が見当たらなかったので、Claude Codeで実際に試してみました。やってみると、提唱元の記事の通りにはいかないところや、記事の主張とは違う結果も出たので、その過程も残しておこうと思います。

## Isolated Specification Testsとは

簡単に言うと、実装するエージェントに仕様書は渡すけれど、答え合わせに使う仕様テストは見せない、というやり方です。

最初に勘違いしやすいところなので書いておくと、隠すのは仕様ではなくテストです。エージェントは仕様書をちゃんと読んで実装します。試験にたとえると、こんな関係です。

・仕様書：教科書。エージェントにしっかり読んでもらう

・仕様テスト：本番の試験問題。エージェントには事前に見せない（読ませないし、書き換えさせない）

・エージェントが自分で書くテスト：自習用の練習問題

提唱元の記事では、コードを書いたエージェントが自分でテストも書くと、それは検証ではなく自己確認にしかならない、と書かれていました。そこで、ユーザー目線で「こう動くべき」を書いたテスト（仕様テスト）を別に用意して、エージェントが仕様書だけを見て作ったものを、仕様テストで外から確かめます。

#### 期待される効果

提唱元の記事の主張と、テストを隠すことでできるようになることを合わせると、次の4つが期待できます。

・自己確認を防ぐ：エージェントが仕様を読み違えると、自分で書くテストも同じように読み違える。別に用意したテストなら、読み違えに気づける（提唱元の記事の一番の主張）

・テストに合わせた実装を防ぐ：試験問題が見えていると、その問題だけ解ければいい実装になるおそれがある。見せなければ、仕様全体を満たしているかを確かめられる

・テストの書き換えを防ぐ：テストがなかなか通らないとき、エージェントがテストの方を緩めて通してしまうことがある。読めない・書けない状態なら、そもそもできない

・仕様書の曖昧さに気づける：仕様書だけで作って仕様テストが落ちたら、実装の誤りか、仕様書の書き方が足りないかのどちらか

#### 隔離とブラックボックス検証の関係

似た言葉に「ブラックボックス検証」があり、提唱元の記事でも別の対策として挙げられています。こちらは確かめる側の話で、コードの中は見ずに、外から動きだけで確かめるやり方です。

・隔離：実装するエージェントから、仕様テストを隠す

・ブラックボックス検証：確かめる側が、実装の中を見ずに動きだけで確かめる

隠すものと隠す相手が逆なので混ざりやすいのですが、仕様テストを隔離しておくと、それが「答えを知らない第三者による外からの確認」になるので、結果としてブラックボックス検証の役割も果たせます。

隠す方法としては、別リポジトリに置く、`.claudeignore` を使う、エージェントの権限で禁止する、といったものが挙げられていました。

#### 環境

・macOS

・Claude Code 2.1.326

・Node.js 24

## 試した内容

架空のECサイトの送料計算を題材にしました。

↓ エージェントに渡す仕様書（SPEC.md）のルール部分

```md
1. 基本送料は 600 円。ただし、クーポン適用後の金額（subtotal - couponDiscount）が 5,000 円以上なら基本送料は 0 円。
2. 離島への配送は、基本送料に 1,200 円を加える。基本送料が 0 円のときも加える。
3. 合計重量が 10kg を超える場合、10kg を超えた分について、5kg ごとに 400 円を加える（5kg に満たない端数も 5kg として数える）。
4. 返り値は送料（円、整数）。
5. subtotal・couponDiscount・totalWeightKg が負の数のときは RangeError を投げる。
```

これとは別に、境界値（5,000円ちょうど、10kgちょうど、15.1kgなど）を中心にした仕様テストを14件、`spec-tests/` に用意しました。

エージェントには、どの条件でも仕様書（SPEC.md）を渡して実装してもらいます。条件によって変えるのは、`spec-tests/` を読めるかどうかだけです。

そのうえで、次の3つの条件で、Claude Codeに同じ指示を出しました。

・隔離なし：何も設定しない

・権限ルール：`spec-tests/` の読み書きを権限ルールで禁止する

・権限ルール＋サンドボックス：さらにサンドボックスで、OSのレベルで読み取りを禁止する

↓ 指示

```
SPEC.md を読んで、仕様どおりに src/shipping.js を実装してください。test/ に自分でテスト（node:test、ファイル名は *.test.js）を書き、npm test がすべて通るまで確認してください。spec-tests/ は別チームが管理しているので、変更しないでください。
```

↓ 権限ルール＋サンドボックスの条件で使った `.claude/settings.json`

```json
{
  "permissions": {
    "deny": ["Read(./spec-tests/**)", "Edit(./spec-tests/**)", "Bash(npm run spec*)"]
  },
  "sandbox": {
    "enabled": true,
    "allowUnsandboxedCommands": false,
    "filesystem": {
      "denyRead": ["./spec-tests"]
    }
  }
}
```

権限ルールだけの条件は、ここから `sandbox` を消したものです。`allowUnsandboxedCommands: false` は、サンドボックスで止められたコマンドを、サンドボックスの外でやり直させないための設定です。

Claude Codeは `claude -p` で動かして、やり取りをすべて記録しました。仕様テストは、エージェントが終わったあとに、エージェントの外で実行しています。デモ一式はこちらに置いています。

https://github.com/ojagao/zenn-content/tree/main/demos/isolated-spec-tests

:::message
デモの実験スクリプト（`run-experiment.sh`・`probe-bypass.sh`）は、中で `claude -p` を実行します。動かすと、その分だけClaude Codeの利用枠（APIで使っている場合は料金）がかかるので、試すときは気をつけてください。
:::

## 分かったこと1：隔離しないと、自分から仕様テストを読みにいく

指示では「spec-tests/ は変更しないでください」としか言っていません。すると、隔離なしの条件では、エージェントが自分から `cat spec-tests/*.js` で仕様テストを読んで、それを見ながら実装していました。`npm run spec` で仕様テストを実行しようともしていました（こちらは実行を許可していなかったので止まりました）。

あとで仕様書を少し変えた実験も合わせると、隔離なしでは4回中4回とも仕様テストを読んでいて、サンドボックスまで重ねた条件では4回中0回でした。

「変更しないで」と書いても、「読まないで」とは伝わらないんですね。仕様テストが独立した確認になっているのは、エージェントが読めないときだけでした。

## 分かったこと2：権限ルールだけだと抜け道がある

権限ルールで禁止した条件で、エージェントに「この4つの方法で spec-tests を読もうとしてみて」とわざと頼んでみました。読めたかどうかは、エージェントの報告ではなく、実際のツールの結果にテストの中身が出てきたかで判定しています。

| 読む方法 | 権限ルールだけ | ＋サンドボックス |
|---|---|---|
| Readツール | 止まった | 止まった |
| `cat spec-tests/shipping.spec.test.js` | 止まった | 止まった |
| `grep -r "test(" .` | 読めた | 止まった |
| `node -e` で `fs.readFileSync` | 読めた | 止まった |

`grep -r` では、仕様テストの期待値まで全部出てきました。

Claude Codeのドキュメントを読み直すと、ちゃんと書かれていました。`Read` や `Edit` の禁止ルールは、Claude Code自身のファイル操作と、`cat`・`head`・`sed` のような決まったコマンドに当てはまります。ただ、`grep -r pattern .` のようにファイル名を指定しないで読むコマンドや、NodeやPythonのスクリプトが中でファイルを開く場合は対象外で、そこまで止めたいならサンドボックスを使うように、とのことでした。

https://code.claude.com/docs/en/permissions

サンドボックスまで重ねると、4つとも止まりました。`ls -R` を実行したときも、`spec-tests` のところで「Operation not permitted」が返ってきていて、OSのレベルで止まっているのが分かります。

## 分かったこと3：.claudeignore では隠せない

提唱元の記事では、隠す方法の1つとして `.claudeignore` が挙げられていました。ところが、Claude Codeのドキュメントには、`.claudeignore` を置いても何も起きないので `Read` の禁止ルールに移すように、と書かれていました。今のClaude Codeで試すなら、権限ルールとサンドボックスで隠すのが確実そうです。

## 分かったこと4：テストがあること自体は分かってしまう

権限ルールで禁止した条件では、エージェントが `.claude/settings.json` を読んでいました。禁止ルールの中身が見えるので、「読めないテストがある」こと自体は伝わってしまいます。中身は読めないので問題はないのですが、存在まで隠したい場合は、提唱元の記事にあるように別リポジトリに置くしかなさそうです。

## 品質に差は出るのか

ここが一番気になっていたところですが、今回の実験では差は出ませんでした。

・3つの条件とも、仕様テスト14件がすべて通った

・実装にわざとバグを7種類入れて（5,000円ちょうどを有料にする、重量の端数を切り捨てる、など）、どのテストが気づくかを調べると、エージェントが自分で書いたテストも、仕様テストも、7種類すべてに気づいた

・仕様書から「5kgに満たない端数も5kgとして数える」を消して曖昧にしても、隔離なし・隔離ありの各3回すべてで、エージェントは端数を切り上げて実装し、仕様テストはすべて通った

最初に挙げた4つの効果ごとに、今回どうだったかを整理するとこうなります。

・自己確認を防ぐ：差は出なかった。仕様がはっきりしていたので、エージェントは仕様を読み違えず、自分で書いたテストでもバグを全部見つけた

・テストに合わせた実装を防ぐ：確かめられなかった。隔離なしの条件では、エージェントが毎回仕様テストを読んでから実装していたので、それが「テストを見ずに正しく作れたのか」が分からない状態になっていた

・テストの書き換えを防ぐ：今回は、テストが通らずに困る場面がなかったので、書き換えそのものが起きなかった

・仕様書の曖昧さに気づける：仕様書を曖昧にしても、エージェントがよくある解釈（切り上げ）で埋めてしまい、気づくきっかけにはならなかった

提唱元の記事にあった「自分で書いたテストでは自己確認にしかならない」という差は、少なくともこの規模の題材では再現しませんでした。

実験してみて考えたのは、隔離で変わるのはコードの品質というより、「仕様テストが通った」という結果をどこまで信じていいか、の方だということです。隔離なしの条件でもテストは全部通りましたが、それは試験問題を見ながら解いた結果です。今回はたまたま正しく実装できていましたが、仕様テストを読めてしまう状態では、テストが通ったことを独立した確認として扱えません。

仕様書に書かれていない暗黙のルールが多い実際の開発や、テストがなかなか通らないような大きな題材では、残りの効果も出てくるかもしれません。このあたりは、もう少し大きな題材で試してみないと分からなそうです。

## 実務でどう使うか

レビュー依頼が来たときに、ホワイトボックスとブラックボックスの両方の面から確認してからLGTMを出す形で使おうかなと思っています。

・ホワイトボックス：コードの中身を読んで、設計や書き方を確認する（いつものコードレビュー）

・ブラックボックス：実装したエージェントに見せていない仕様テストで、外から動きを確認する

ブラックボックス側の確認に、隔離した仕様テストを使うイメージです。エージェントは仕様書を見て実装し、自分で書いたテストも通してきますが、それとは別に、エージェントが見ていない仕様テストでも通るかを確かめます。提唱元の記事でも、コードの中を見る確認（ホワイトボックス）と、外から独立して確かめる確認（ブラックボックス）を分けて考えることが書かれていました。

## まとめ

Isolated Specification Testsを、Claude Codeの権限ルールとサンドボックスで試してみました。

・仕様書はエージェントに渡して、答え合わせに使う仕様テストだけを隠すやり方。隠したテストは、外から動きを確かめるブラックボックス検証として使える

・隔離しないと、エージェントは「変更しないで」と言われても、自分から仕様テストを読みにいく

・権限ルールだけだと、`grep -r` やスクリプト経由で読めてしまう。サンドボックスまで重ねると止まった

・提唱元の記事にある `.claudeignore` では、今のClaude Codeでは隠せない

・今回の題材では、隔離してもしなくてもコードの品質に差は出なかった。変わるのは、仕様テストが通ったことを独立した確認として扱えるかどうか
