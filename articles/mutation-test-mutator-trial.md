## はじめに

mizchiさんのミューテーションテストの記事を読んで、勤務している会社のプロダクトでも試してみました。

https://zenn.dev/mizchi/articles/mutation-test-quality

元の記事では、AIでテストカバレッジを上げるのは簡単になったけれど、そのテストが本当に何を確かめているのかは分からない、という問題が書かれていました。そこで紹介されていた `@mizchi/mutator` を、実際のプロダクトのコードに当ててみた結果を残しておこうと思います。

導入から実行、結果の整理までは、Claude Codeに任せています。

:::message
業務のプロダクトなので、プロダクトの内容やコードは書けません。ツールの使い方と、数字や見つかったものの種類だけを書いています。
:::

## ミューテーションテストとは

簡単に言うと、実装のコードをわざと少しだけ壊して、テストがそれに気づくかを確かめる方法です。

`>` を `>=` に変える、条件を常に `false` にする、戻り値を書き換える、といった変更（ミュータント）を自動で作って、1個ずつテストを流します。

・Killed：テストが落ちた。テストがその変更に気づけた

・Survived：テストが通ってしまった。テストがその変更を見逃している

ただし、どんな入力でも結果が変わらない「等価ミュータント」もあるので、生き残ったものが全部テストの穴というわけではありません。詳しくは元の記事がとても分かりやすいので、そちらを読んでみてください。

#### 環境

・Node.js 24.22

・Vitest 5.0.5（単体・結合・E2Eを projects で分けている構成）

・TypeScriptのバックエンド（NestJS、デコレータの変換にSWCを使用）

・@mizchi/mutator 0.4.4

・Claude Code

## 導入

本体のブランチを汚さないように、Claude Codeのworktreeで完全に別のブランチを切って試しました。

↓ インストール

```bash
npm install -D @mizchi/mutator@0.4.4
```

既存のVitestの設定は単体・結合・E2Eに分かれていて、結合テストやE2EはDBを使うので1本が長いです。ミュータントの数だけテストを繰り返すので、単体テストだけを流す設定を別に作りました。

↓ ミューテーションテスト用のVitestの設定（簡略化しています）

```ts
import { defineConfig } from 'vitest/config';
import baseConfig from './vitest.config';

// 単体テストだけを流す。結合テストと E2E は 1 本が長いので、ミュータントごとに繰り返す対象にしない
const { projects: _projects, ...baseTestOptions } = baseConfig.test ?? {};

export default defineConfig({
  ...baseConfig,
  test: {
    ...baseTestOptions,
    include: ['src/**/*.spec.ts'],
    exclude: ['**/node_modules/**', '**/*.integration.spec.ts', 'src/**/*.e2e.spec.ts'],
  },
});
```

↓ 実行（対象は1つの機能のドメイン層だけ）

```bash
npx mutator --config vitest.mutation.config.ts --include 'src/<対象の機能>/domain/**/*.ts' --reporter text --reporter json --reporter html
```

`--config` はVitest側の設定ファイルの指定です。mutator自体の設定ファイルを指定する `--config-file` とは別物なので、元の記事にもあるように注意が必要です。

projectsで分けた構成や、SWCでデコレータを変換している構成で動くかが確認ポイントでしたが、既存の設定を読み込む形のまま、書き換えなしで動きました。

## 結果

対象にしたのは、状態の遷移や期限の判定が集まっているドメイン層です。

| 項目 | 値 |
|---|---|
| 対象 | 18ファイル（約1,300行） |
| ミュータント | 973個（型チェックで319個を除外し、654個を判定） |
| 検出（Killed） | 560個（うちタイムアウト4個） |
| 生き残り（Survived） | 80個 |
| どのテストも通らない（NoCoverage） | 14個 |
| スコア | 85.6% |
| 実行時間 | 初回541秒、変更なしで再実行すると約3秒 |

初回に9分かかったのは、単体テスト333ファイルを一度すべて流して、どのテストがどのコードを通るかを調べるためです。2回目以降は結果を使い回すので、変更がなければ3秒で終わりました。

型チェックで落ちるミュータントを先に除外してくれるので、973個のうち3分の1ほどは、テストを流す前に省かれていました。

## 何が見つかったか

正直、バグがいくつか出てくるのかなと思っていたのですが、実装のバグは1件も見つかりませんでした。

見つかったのは、コードには正しく書いてあるのに、壊してもテストが1本も落ちないルールです。同じ原因のものをまとめると、次の7件になりました。

・設定値の上限と下限が逆転しているときに弾くルール

・どのテストも通っていない分岐

・ありえない状態の遷移を不正として検知するルール

・期限ちょうどの時刻の扱い（`<=` を `<` に変えても落ちない）

・件数を返す関数（戻り値を常に1にしても落ちない）

・HTTPステータスの範囲判定の下限（400未満を渡すテストがない）

・特定の状態の組み合わせのときに処理しないルール

1つ目の上限と下限の逆転は、境界のテストや「上限が0」のテストはあるのに、逆転だけが抜けていました。コードのコメントにはルールとして書いてあったので、書いたつもりで守れていなかった例です。いま誤動作しているわけではないのですが、逆にしても検出できないというのは、もし実際に起きたらCriticalな問題だなと感じました。

#### 割り引いて見るもの

生き残りとどのテストも通らないものを合わせた94個が、全部テストの穴だったわけではありません。

・エラーメッセージの文言を空にする変更：36個。文言まで固定するテストを書くかどうかの話で、ルールの穴ではない

・入力検証まわり：27個。エラーに出す項目名の組み立てなど

・上の7件にまとめたもの：31個

31個の中にも等価ミュータントが混ざっていて、たとえば `undefined` との比較が常に偽になる箇所は、書き換えても結果が変わらないので、テストを足しても消せないものでした。

## 穴を塞ぐテストを足す

7件それぞれを守るテストを、テストだけの変更として足しました。実装には触れていません。

| | 追加前 | 追加後 |
|---|---|---|
| 検出 | 560 | 578 |
| 生き残り | 80 | 63 |
| どのテストも通らない | 14 | 10 |
| スコア | 85.6% | 88.8% |

狙った7件の生き残りはすべて消えました。このときの実行は、変更したテストに関係するミュータントだけを流し直す形になっていて、126個を実行して525個は前回の結果を使い回し、222秒で終わりました。

## 気づいたこと

#### スコアは揺れる

ある定数を書き換えるミュータント2個が、1回目はタイムアウト（検出扱い）で、2回目は生き残りになりました。タイムアウトで検出扱いになっているものは、実行のたびに結果が変わりうるので、スコアをCIの合否の基準にするのは向かなそうです。元の記事でも、決定的な指標というより、リファクタリングの指標として扱うものだと書かれていました。

#### ツールの更新がとても速い

試した日に0.4.4が出たばかりで、その2日で5回リリースされていました。業務のリポジトリに入れておくなら、バージョンは固定しておいた方がよさそうです。

#### Claude Codeに任せたところ

導入、実行、生き残ったミュータントの一覧から等価ミュータントかどうかを見分けて、テストの穴になっているものを7件にまとめるところ、テストを書くところまで、Claude Codeに任せました。mutatorのパッケージには使い方のSKILLが同梱されていて、Claude Codeはそれを読んでから導入していました。元の記事にも、AIはミューテーションテストのツールの運用がうまく、結果を見てテストを直すのがうまい、と書かれています。

## 使ってみた感想

バグが出るかと思っていましたが、元の記事でカバレッジだけでは保証できないと言っている通り、ミューテーションテストはバグを探すものというより、テストの不完全性を補うものだなと感じました。実際、見つかった7件の多くは、テストが実行している行の中にありました。

導入も、既存のVitestの構成のまま書き換えなしで動いたので、簡単でした。

## これからの使い方

CIで毎回回すのではなく、作業ブランチで時々回して、生き残ったものを見てテストを直す使い方にしようと思っています。元の記事でおすすめされている使い方と同じです。

## まとめ

・実際のプロダクトのドメイン層（約1,300行）で、スコアは85.6%から始まり、テストを足して88.8%になった

・実装のバグは0件。見つかったのは、正しく書いてあるのに壊してもテストが落ちないルールが7件

・生き残りの中には、エラーメッセージの文言や等価ミュータントも多いので、1個ずつ見て判断する必要がある

・初回は9分、変更なしの再実行は3秒。スコアはタイムアウトの影響で揺れるので、合否の基準には向かない
